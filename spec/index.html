    aipostex Grounded Spec¶

    aipostex is a single-binary offensive security tool for AI infrastructure. The current product shape is:

    • discovery on disk with AI-focused rules
    • network fingerprinting plus template-driven assessment
    • guarded post-exploitation modules for Ollama, vector databases, Jupyter, MCP, and generic OpenAI-compatible endpoints
    • first-class enum-to-proof modules for Ray, MLflow, and Gradio

    This spec is intentionally layered so we separate what is real now from what the next offensive roadmap should add.

    Implemented Now¶

    Assessment loop¶

    • scan
    • scan-files
    • scan-network
    • templates
    • template-info

    Current behavior:

    • built-in YAML templates plus optional operator-supplied template directories
    • deterministic finding deduplication before output
    • source-aware console output, JSON, and JSONL
    • stderr summaries for discovery, scan, template, and exploit commands
    • workflow guidance on scan-network and read-oriented exploit commands so discovery results hand off into concrete follow-on commands
    • network discovery for Ollama, ChromaDB, Qdrant, Weaviate, Jupyter, generic OpenAI-compatible APIs, MCP-over-HTTP/SSE, MCP Inspector signals, and adjacent AI services already present in the scaffold

    Post-exploitation modules¶

    Implemented command surface:

    aipostex ollama enum|prompts|generate|show|running|copy|create|delete|poison
aipostex vectordb --type chromadb|weaviate|qdrant enum|extract|search-sensitive
aipostex jupyter enum|kernels|notebooks|read-notebook|exec
aipostex mcp analyze|enum|poison
aipostex openai-compat auth-sweep|enum|validate-inference|prompt-extract|throughput|proxy-test
aipostex ray enum|jobs|job-logs|job-artifacts|submit|runtime-env
aipostex mlflow enum|experiments|runs|artifacts|registry|model-versions|model-artifacts|download-artifact
aipostex gradio enum|predict|queue-probe|upload-file|download-file|file-chain|serve-probe

    Current module truth:

    • ollama supports read-only enumeration plus guarded mutating model operations
    • vectordb supports read-oriented enum/extract/search across ChromaDB, Weaviate, and Qdrant
    • jupyter supports enumeration, notebook reads, and guarded kernel execution
    • mcp analyze now handles common config layout variants, surfaces transport choices, local command execution, plaintext credential-bearing env entries, non-loopback exposure, inspector/debug local risk, tool-shadowing risk, and chain-aware remote MCP follow-ons when config or inspector material references remote URLs
    • mcp enum classifies exposed tools into fetch/file/exec/process/inspector-style buckets with confidence, adds prompt/resource correlation, and includes inspector/debug detection
    • mcp poison now supports explicit modes:
    • generic
    • ssrf-cloud
    • cmd-inject
    • path-traversal
    • mcp poison now records proof strength more precisely:
    • generic payload accepted
    • provider-marker cloud metadata
    • likely-executed vs possible-echo command injection
    • file-read-confirmed vs path-disclosure traversal
    • openai-compat now adds weak-auth classification, richer model normalization/value scoring, bounded inference coherence scoring, bounded prompt-classification, and opt-in throughput/proxy validation
    • ray now covers dashboard metadata, visible jobs, bounded job detail/log reads, bounded job-artifact correlation, guarded proof-job submission through the jobs API, and guarded runtime-env validation
    • mlflow now covers tracking metadata, experiments/runs discovery, bounded artifact-tree inspection, exposed registry enumeration, model-version correlation, bounded model-artifact listing, and bounded artifact reads
    • gradio now covers config discovery, queue/file capability classification, bounded prediction calls, bounded file reads, bounded file-chain correlation, and guarded queue/upload/serve proofs

    Built-in offensive coverage¶

    Implemented built-ins now include:

    • Ollama unauthenticated API exposure
    • Ollama system prompt extraction
    • ChromaDB unauthenticated API exposure
    • Weaviate unauthenticated API exposure
    • Qdrant unauthenticated API exposure
    • Jupyter unauthenticated API and terminal exposure
    • MCP unauthenticated HTTP and SSE exposure
    • MCP fetch SSRF checks for CVE-2025-65513-style localhost bypass patterns
    • MCP Inspector exposure
    • MCP Inspector API exposure
    • MCP Host-header trust / DNS rebinding signal
    • campaign coverage for Bizarre Bazaar-style endpoint validation, placeholder key acceptance, model inventory exposure, and unauthorized inference
    • Ray unauthenticated dashboard and jobs API exposure, aligned to jobs -> logs -> takeover workflows
    • MLflow unauthenticated tracking and artifact-surface exposure, aligned to registry/model-artifact follow-ons
    • Gradio config and callable API surface exposure, aligned to upload/read/serve chain potential

    Next Tranche¶

    The current tranche has already deepened openai-compat, Ray, MLflow, and Gradio. The next tranche should build on that depth rather than redoing it.

    OpenAI-compatible offensive validation¶

    Still reasonable next within openai-compat:

    • provider-specific deep exploit paths only where generic OpenAI-compatible behavior diverges materially
    • stronger resale-value reporting tied to longer campaign outputs rather than one-off findings

    Campaign alignment¶

    Still reasonable next for Bizarre Bazaar emulation:

    • broader placeholder/test-key corpora if real-world patterns continue to expand
    • campaign-level reporting that summarizes accepted auth patterns, model value, and throughput in one artifact

    Near-Term Offensive Roadmap¶

    These items should be treated as the near-term offensive backlog, not vague aspirations.

    MCP P0 exploit coverage¶

    Explicit offensive roadmap items:

    • credential extraction from config env blocks
    • cloud metadata SSRF through fetch-like tools
    • command injection through shell/process-like tools
    • path traversal through file-read/write tools
    • inspector exposure
    • DNS rebinding / Host-header trust checks
    • tool shadowing analysis across configured servers

    Generic inference exploitation¶

    openai-compat is the generic post-exploitation path for:

    • OpenAI-compatible APIs
    • vLLM
    • LiteLLM
    • LocalAI
    • LM Studio

    Near-term additions should stay here rather than cloning provider-specific commands unless the target diverges materially.

    Broader service depth backlog¶

    The next offensive depth work after MCP and generic inference is deeper service-family coverage for:

    • Ray cluster and runtime takeover paths beyond the current bounded submit|runtime-env proofs
    • MLflow registry, model, and artifact abuse beyond the current bounded correlation and read flows
    • Gradio upload, queue, and file-abuse depth beyond the current bounded file-chain and serve probes

    Runtime and OPSEC foundation¶

    This foundation is now implemented in the current binary:

    • context.Context propagation through long scans and exploit workflows
    • shared --proxy transport support for HTTP, HTTPS, and SOCKS5
    • working --stealth behavior with jitter, User-Agent rotation, and worker/concurrency caps
    • embed.FS for built-in templates and discovery rules
    • JSONL-first guidance for long-running, crash-tolerant output
    • scan-network --max-hosts CIDR size guardrails
    • HTTPS-aware probing plus global --insecure transport support

    Current operator contract for runtime behavior:

    • built-in templates and rules come from the binary by default
    • custom --templates-dir content loads after embedded templates and may override duplicate IDs
    • custom --rules-dir content loads after embedded rules
    • Ctrl+C cancels in-flight work cleanly and preserves findings already written

    Later Platformization¶

    These remain later-phase foundation items, not part of the already-landed runtime tranche.

    Runtime and OPSEC roadmap¶

    • credential chain-loading from file discovery into exploit modules
    • deeper transport heuristics and proxy auth support if needed
    • stronger long-running job orchestration and resumability

    Deferred platform features¶

    • SQLite output
    • scan-all
    • report
    • validate
    • non-HTTP transports
    • external billing-sensitive credential validation against third-party SaaS APIs

    Safety Model¶

    The operator contract is:

    • read-only enum and extract workflows run without --force-exploit
    • higher-noise or state-changing workflows require --force-exploit
    • default scan and scan-network stay low-noise
    • aggressive cloud metadata access, command injection, path traversal, throughput probing, and proxy validation do not run during default scans

    Current gated actions:

    • Ollama: copy, create, delete, poison
    • Jupyter: exec
    • MCP: poison in every mode
    • OpenAI-compatible: throughput, proxy-test
    • Ray: submit, runtime-env
    • Gradio: queue-probe, upload-file, serve-probe

    Additional runtime defaults now in force:

    • --max-hosts defaults to 65536 for scan-network; 0 disables the guardrail
    • --stealth caps scan and scan-network concurrency to 1
    • --stealth caps file-scanning workers to 1

    Output Contract¶

    Supported outputs:

    • console
    • json
    • jsonl

    Contract rules:

    • pkg/report.Finding top-level fields remain the stable shared finding schema
    • stdout is for findings/output-writer content
    • stderr is for progress, warnings, blocked exploit messaging, summaries, and follow-on Next actions guidance
    • findings may reserve metadata.workflow for structured follow-on guidance and metadata.evidence for display-safe evidence preview metadata
    • ordinary finding metadata may carry proof_stage, proof_strength, chain_source, and capability_labels to keep console and machine-readable outputs aligned on staged exploit chains
    • console output may render redacted evidence while JSON and JSONL preserve the underlying evidence payload
    • jsonl is the recommended file-backed format for long-running scans because it streams incrementally

    Operator progression¶

    The current operator contract is not just "run a command, read a finding." It is:

    • discovery commands identify reachable AI surfaces and attach read-first follow-on commands for the matching exploit module
    • read-oriented exploit commands attach the next concrete command using discovered values when available, such as model IDs, auth-pattern classifications, collection names, notebook paths, kernel IDs, MCP remote URLs and capability categories, Ray job IDs and artifact references, MLflow experiment/run/model-version/artifact identifiers, or Gradio endpoint/file references and returned handles
    • suggestions that require higher noise or target-state changes are emitted after read-only suggestions and remain gated by --force-exploit
